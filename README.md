# MCP-Codex-GraphDB experiments

This repository contains an experiment in which OpenAI's Codex (AI agent build by OpenAI) answered questions
about Business Process Model and Notation (BPMN) and Working Environment models stored as RDF knowledge graphs
in Ontotext GraphDB (RDF triplestore). It includes the process data, the questions, the answers generated by Codex, the gold answers/ground truths and the Python script used to score the agent-generated answers.

This experiment was set up and tested on Windows 11. The commands, file paths and installation steps are written for Windows. I suppose macOS and Linux users can still follow the same general workflow, but some paths and setup steps - especially those for Bee-Up - will most likely need to be adapted.

Sidenote: Yes, there are many instructions, but with a reason (for this madness). This repository tried to include the little things that helped me crawl my way out of the obstacles encountered.

Installing the entire system just to check the published
results is not necessary. There are a few different ways to use this repository:

| What you want to do | What you need |
| --- | --- |
| Read the questions, answers and results | Only this repository |
| Recalculate the scores from the saved answers | Python 3.10 or newer |
| Ask Codex the questions again | GraphDB, Docker, the retrieval service and Codex |
| Change the BPMN & Working Environment models before exporting it again | Bee-Up 1.7 |

If you only want to run the evaluator, start with the next section. If you want
to rebuild the whole experiment, go to
[Running the experiment again from scratch](#running-the-experiment-again-from-scratch).

## The quick route: run the evaluator

### 1. Download this repository

Open the
[GitHub repository](https://github.com/DamarisDd/MCP-Codex-GraphDB-experiments),
select **Code** and then select **Download ZIP**. Extract the ZIP wherever you
want to keep the project.

If you already have Git, you can clone it instead:

```powershell
git clone https://github.com/DamarisDd/MCP-Codex-GraphDB-experiments.git
cd .\MCP-Codex-GraphDB-experiments
```

If `git` is not recognized, either use the ZIP option or install
[Git for Windows](https://git-scm.com/download/win). After installing it, open a
new PowerShell window and check it:

```powershell
git --version
```

The commands in this README assume that the folder is called
`MCP-Codex-GraphDB-experiments` (exactly as is after downloading or cloning it). A ZIP download may add `-main` to the folder
name. That is fine—just use the actual folder name in your commands.

### 2. Install Python

Install [Python for Windows](https://www.python.org/downloads/windows/) 3.10 or
newer (version 3.14.3 was used for the current experiments). During installation, select **Add Python to PATH**.

Open a new PowerShell window and check that Python works:

```powershell
python --version
```

If Windows recognizes `py` but not `python`, use `py` instead in the commands
below. The evaluator uses only Python's built-in modules, so there are no extra
packages to install.

### 3. Run `evaluate_generated_answers.py`

Open PowerShell in the repository folder (the folder containing this README). Then run:

```powershell
python .\scripts\evaluate_generated_answers.py `
  --gold .\scripts\gold_answers_all.jsonl `
  --transcripts .\scripts\transcripts `
  --schema .\scripts\schema\answer_schema.json `
  --predictions-out .\scripts\predictions-out\predictions_all.jsonl `
  --report .\scripts\report\evaluation_all_report.json `
  --csv .\scripts\csv\evaluation_all_per_run.csv `
  --expected-runs 3 `
  --match hybrid
```

That command does the entire evaluation. It reads the 189 saved transcripts,
finds the generated answer in each one, puts those answers into a single JSONL
file, compares them with the gold answers and rewrites the JSON and CSV result
files.

If you already have a predictions JSONL file (which is the file containing
the agent generated answers extracted from the transcripts) and do not want 
to read the transcripts again, replace:

```powershell
--transcripts .\scripts\transcripts
```

with:

```powershell
--predictions .\scripts\predictions-out\predictions_all.jsonl
```

To see every available option, run:

```powershell
python .\scripts\evaluate_generated_answers.py --help
```

## What was tested

The experiment used:

- one GraphDB repository named `bpmn_judicial`;
- 63 questions;
- three separate runs for every question;
- 189 saved transcripts in total;
- 55 structured-answer questions and 8 yes/no questions; and
- 43 list answers, 4 paths, 4 rankings, 3 values and 1 finding.

The questions were divided into six groups:

| Category | Questions | What they ask about |
| --- | ---: | --- |
| C1 | 14 | Process-element identification/existence and containment |
| C2 | 9 | Control flow ordering, routes/paths, outcomes and work done in parallel |
| C3 | 23 | Responsibility organizations, time, cost and route analysis |
| C4 | 8 | Documents and how they are produced or used |
| C5 | 5 | Participants, messages and communication |
| C6 | 4 | Process weaknesses and improvement opportunities |

Codex was instructed to answer only with information from the
`bpmn_judicial` repository in GraphDB. Depending on the question, it could use all GraphDB
exposed tools, including SPARQL, full-text or retrieval search. The saved
transcripts include the question, the GraphDB tool calls, the tool results and
the final answer. This makes it possible to see not only what Codex answered,
but also how (through what means) it reached that answer.

Codex was also given two assumptions about the process model - to help with the evaluation:

- every element inside an ad-hoc subprocess is executed and completed once;
  and
- an interrupting subprocess boundary event may occur after exactly one
  internal task has finished and before the next internal or external element
  is selected.

The full instructions are in
[agent_personalization.txt](agent%20instructions/agent_personalization.txt). The
[deployment diagram](Codex-MCP-GraphDB%20coupling%20-%20deployment%20diagram.bmp)
shows how the components in this experiment were coupled.

## Running the experiment again from scratch

This part explains how to generate a new set of answers. It looks long because
several programs have to talk to one another, but each program has a fairly
simple role:

- GraphDB stores and queries the RDF data;
- Weaviate stores the vector embeddings;
- the OpenAI retrieval service sits between GraphDB and Weaviate;
- GraphDB's MCP endpoint gives Codex access to the query tools; and
- Codex answers the questions.

You will need a ChatGPT account with access to Codex and the model used in the
experiment. You will also need an
[OpenAI API key](https://platform.openai.com/api-keys) with API billing enabled
for `text-embedding-3-large`. ChatGPT subscriptions and API billing are
separate. Creating embeddings can, therefore, incur an API cost.

The setup uses local ports 7200, 8000, 8080 and 50051. Make sure another
program is not already using them.

### 1. Bee-Up is optional

You do not need to install Bee-Up to run the saved evaluation or to load the
RDF data supplied in this repository. Install Bee-Up only if you want to change 
the process model, create a different one or produce a new Bee-Up RDF export 
before running the experiment.

If you do need it:

1. Open the official [Bee-Up page](https://bee-up.omilab.org/activities/bee-up/).
2. Find the **Download** section and download Bee-Up 1.7 for Windows.
3. Extract the downloaded package.
4. Run `install_on_windows.msi` and follow the installer.
5. Install a Java runtime compatible with Java 8 if you want to use Bee-Up's
   RDF export function.

All the original editable models are included as
[`editable Bee-Up model package.adl`](context/editable%20Bee-Up%20model%20package.adl).
Use this file in Bee-Up if you want to inspect or modify the models and export
the RDF again. The `.trig` files supplied in the same folder are the Bee-Up RDF exports
used with GraphDB.

### 2. Install GraphDB 11.4

The experiment used GraphDB 11.4 Desktop.

1. Open the official
   [GraphDB download page](https://www.ontotext.com/products/graphdb/).
2. Request the Windows installer and choose GraphDB 11.4 if the site asks which
   version you need.
3. Run the downloaded `.msi` installer.
4. Start GraphDB Desktop from the Windows Start menu.
5. Select **Open GraphDB Workbench** or open
   [http://localhost:7200/](http://localhost:7200/) yourself.

GraphDB Desktop includes its own Java runtime. You do not need to install Java
for GraphDB. The separate Java requirement mentioned above applies only to
Bee-Up's RDF export.

### 3. Install Docker Desktop

1. Follow Docker's official
   [Windows installation guide](https://docs.docker.com/desktop/setup/install/windows-install/).
2. Use the WSL 2 backend when the installer offers it.
3. Restart Windows if asked.
4. Open Docker Desktop and wait until it says that the Docker engine is running.
5. Open a new PowerShell window and check both commands:

```powershell
docker --version
docker compose version
```

### 4. Download the OpenAI ChatGPT Retrieval Plugin

Despite its name, this is not something you install from Codex's Plugins page.
It is a standalone API created by OpenAI. GraphDB sends text to that API and
the API stores and searches embeddings in Weaviate.

Clone it beside this repository:

```powershell
cd ..
git clone https://github.com/openai/chatgpt-retrieval-plugin.git
cd .\chatgpt-retrieval-plugin
git checkout b28ddce58474441da332d4e15c6dd60ddaa953ab
```

The commit is pinned so that everybody starts from the same plugin code. The
old ChatGPT plugins product is deprecated, but this code is used here only as a
local retrieval API.

### 5. Prepare the Docker and environment files

The Compose file in this repository is the one used in the experiment. It must
be placed in the cloned `chatgpt-retrieval-plugin` folder because it builds the
plugin using `context: .` and the plugin's own `Dockerfile`.

While PowerShell is still inside `chatgpt-retrieval-plugin`, copy both templates:

```powershell
Copy-Item ..\MCP-Codex-GraphDB-experiments\docker-compose.yml .\docker-compose.yml
Copy-Item ..\MCP-Codex-GraphDB-experiments\.env.example .\.env
notepad .\.env
```

If your experiment-repository folder has a different name, adjust those two
paths.

Replace `OPENAI_API_KEY` with your own OpenAI API key. Replace `BEARER_TOKEN`
with a long, random secret. You can generate that token at
[jwt.io](https://www.jwt.io/#decoded-jwt) by following the steps in GraphDB's
[retrieval-plugin setup instructions](https://graphdb.ontotext.com/documentation/11.4/retrieval-graphdb-connector.html#setting-up-the-chatgpt-retrieval-plugin).

The non-secret environment settings used in the experiment were:

```dotenv
OPENAI_API_KEY="REPLACE_WITH_YOUR_OPENAI_API_KEY"
EMBEDDING_MODEL="text-embedding-3-large"
EMBEDDING_DIMENSION=1024
BEARER_TOKEN="REPLACE_WITH_YOUR_BEARER_TOKEN"
DATASTORE="weaviate"
WEAVIATE_CLASS="BPMNPROCESS"
```

The actual secrets are deliberately not included. The same bearer token must be
used later when the GraphDB retrieval connector is created.

The Docker setup creates two containers:

- Weaviate 1.38.2, available on ports 8080 and 50051; and
- the OpenAI retrieval API, available on port 8000.

It also uses a retrieval chunk size of 400, an informational logging level and
a Weaviate query limit of 500. These values are already in the supplied Compose
file.

Start the containers and the retrieval API:

```powershell
docker compose up -d --build
docker compose ps
```

Both services should appear as running. Check them with:

```powershell
Invoke-WebRequest http://localhost:8000/docs -UseBasicParsing
Invoke-RestMethod http://localhost:8080/v1/.well-known/ready
```

If the retrieval service starts before Weaviate is ready, wait a few seconds and
restart only that service:

```powershell
docker compose restart retrieval
docker compose logs --tail 100 retrieval
```

To stop both containers without deleting the Weaviate data:

```powershell
docker compose down
```

Be careful with this version:

```powershell
docker compose down -v
```

The `-v` removes the Weaviate volume as well, which means the indexed data is
deleted and must be created again.

### 6. Create the GraphDB repository

Open GraphDB Workbench at [http://localhost:7200/](http://localhost:7200/) and:

1. Go to **Setup → Repositories**.
2. Select **Create new repository**, then **GraphDB Repository**.
3. Set the repository ID to `bpmn_judicial`.
4. You can use the `RDFS-Plus (Optimized)` ruleset.
5. Enable the full-text-search index. Include `default` and `iri`, use `default`
   for `xsd:string` literals and use `iri` for IRI indexing.
6. Select **Create**, then connect to the new repository.

### 8. Create the `text_index` similarity index

The experiment also used GraphDB's text-similarity search. The index was created
directly in GraphDB Workbench:

We first considered a Predication Semantic Index (PSI). It could be queried
directly with its own SPARQL pattern, but, in this setup, it did not return
usable results through MCP's `similarity_search` tool. The likely reason is a
difference in query shape: PSI is organized around RDF predications, while the
MCP tool takes a natural-language query and returns document-style similarity
matches. We therefore used `text_index`, which fits that MCP call directly.
This was a practical choice for this experiment, not a claim that PSI or the
MCP integration is generally limited.

1. Go to **Explore → Similarity**.
2. Select **Create similarity index**.
3. Select **Create text similarity index**.
4. Set the index name to `text_index`.
5. Replace the **Data query** with the query below.
6. Replace the **Search query** with the second query below.
7. Select **Create** and wait for GraphDB to finish building the index.

The data query decides which BPMN elements are indexed and turns the useful
facts about each element into a piece of searchable text:

```sparql
PREFIX rdf: <http://www.w3.org/1999/02/22-rdf-syntax-ns#>
PREFIX rdfs: <http://www.w3.org/2000/01/rdf-schema#>
PREFIX mm: <http://bee-up.omilab.org/rdf/1_7#>
PREFIX cv: <http://www.comvantage.eu/mm#>

SELECT ?documentID ?documentText
WHERE {
    ?documentID
        rdf:type ?elementType ;
        rdfs:label ?elementName .

    VALUES (?elementType ?elementTypeName) {
        (mm:o_Task_BPMN                  "task")
        (mm:o_Sub-Process_BPMN           "subprocess")
        (mm:o_Start_Event_BPMN           "start event")
        (mm:o_Intermediate_Event_BPMN    "intermediate event")
        (mm:o_End_Event_BPMN             "end event")
        (mm:o_Exclusive_Gateway_BPMN     "exclusive gateway")
        (mm:o_Non-exclusive_Gateway_BPMN "non-exclusive gateway")
        (mm:o_Data_Object_BPMN           "data object")
    }

    OPTIONAL {
        ?documentID
            (
                mm:a_Task_type |
                mm:a_Sub-Process_type |
                mm:a_Gateway_type |
                mm:a_Data_type
            )
            ?specializedType .
    }

    OPTIONAL {
        ?documentID cv:described_in ?model .
        ?model rdfs:label ?modelName .
    }

    OPTIONAL {
        ?documentID mm:a_Costs ?cost .
    }

    OPTIONAL {
        ?documentID mm:a_Execution_time ?executionTime .
    }

    OPTIONAL {
        SELECT ?documentID
               (GROUP_CONCAT(
                    DISTINCT STR(?incomingName);
                    separator=", "
                ) AS ?incomingNames)
        WHERE {
            ?incomingFlow
                rdf:type mm:r_Subsequent ;
                cv:from ?incomingElement ;
                cv:to ?documentID .

            ?incomingElement rdfs:label ?incomingName .
        }
        GROUP BY ?documentID
    }

    OPTIONAL {
        SELECT ?documentID
               (GROUP_CONCAT(
                    DISTINCT STR(?outgoingName);
                    separator=", "
                ) AS ?outgoingNames)
        WHERE {
            ?outgoingFlow
                rdf:type mm:r_Subsequent ;
                cv:from ?documentID ;
                cv:to ?outgoingElement .

            ?outgoingElement rdfs:label ?outgoingName .
        }
        GROUP BY ?documentID
    }

    BIND(
        CONCAT(
            "Name: ", STR(?elementName), ". ",
            "Element type: ", STR(?elementTypeName), ".",

            IF(
                BOUND(?specializedType),
                CONCAT(
                    " Specialized type: ",
                    STR(?specializedType),
                    "."
                ),
                ""
            ),

            IF(
                BOUND(?cost),
                CONCAT(
                    " Cost: ",
                    STR(?cost),
                    "."
                ),
                ""
            ),

            IF(
                BOUND(?executionTime),
                CONCAT(
                    " Execution time: ",
                    STR(?executionTime),
                    "."
                ),
                ""
            ),

            IF(
                BOUND(?modelName),
                CONCAT(
                    " Model: ",
                    STR(?modelName),
                    "."
                ),
                ""
            ),

            IF(
                BOUND(?incomingNames),
                CONCAT(
                    " Incoming: ",
                    ?incomingNames,
                    "."
                ),
                ""
            ),

            IF(
                BOUND(?outgoingNames),
                CONCAT(
                    " Outgoing: ",
                    ?outgoingNames,
                    "."
                ),
                ""
            )
        )
        AS ?documentText
    )
}
```

The search query tells GraphDB how to return matching document identifiers and
their similarity scores:

```sparql
PREFIX : <http://www.ontotext.com/graphdb/similarity/>
PREFIX similarity-index: <http://www.ontotext.com/graphdb/similarity/instance/>
PREFIX pubo: <http://ontology.ontotext.com/publishing#>

SELECT ?documentID ?score {
    ?search a ?index ;
        ?searchType ?query ;
        :searchParameters ?parameters ;
        ?resultType ?result .
    ?result :value ?documentID ;
            :score ?score .
}
```

You can test it on the same **Explore → Similarity** page.

### 9. Create the `bpmnprocess` retrieval connector

Make sure the Docker containers are still running. Then:

1. Open the `.env` file in `chatgpt-retrieval-plugin` and copy its
   `BEARER_TOKEN` value.
2. Open
   [bpmnprocess_retrieval_connector_11_4.sparql](scripts/bpmnprocess_retrieval_connector_11_4.sparql).
3. Copy that query into GraphDB Workbench's **SPARQL** editor.
4. In the Workbench copy, replace
   `REPLACE_WITH_THE_SAME_BEARER_TOKEN_AS_IN_DOT_ENV` with the token from `.env`.
5. Make sure `bpmn_judicial` is the selected repository and run the update.
6. Go to **Setup → Connectors** and wait for `bpmnprocess` to finish
   synchronizing.

Do not put the real token into the tracked SPARQL file. Paste it only into the
copy you run in Workbench.

If `bpmnprocess` already exists, running the creation query again will fail.
Remove the old connector from **Setup → Connectors** only when you genuinely
want to rebuild it.

### 10. Check GraphDB's MCP endpoint

GraphDB 11.4 exposes its MCP server here:

```text
http://localhost:7200/mcp
```

This is how Codex receives the GraphDB tools. The MCP endpoint does not contain
a second copy of the data; it simply lets Codex ask the running GraphDB instance
to list repositories, run SPARQL, perform full-text and similarity searches, and
use retrieval search.

Keep this setup on localhost unless you have deliberately configured GraphDB
authentication and network security.

## The answer format

Yes/no questions must be answered with only `Yes` or `No`.

Every other answer must be one JSON object following the supplied schema. It has
three main fields:

- `answer_type`: what kind of answer it is, such as a list, value, ranking or
  path;
- `status`: whether an answer was found or why it could not be provided; and
- `results`: the items or values that answer the question.

Each result has `identifier`, `label`, `element_type`, `rank`, `attributes` and
`related_elements`. Fields that do not apply are left `null` or empty.

Why use one schema when not every question needs every field? Because the
evaluator can always find the answer in the same place. It does not need a
different parser for lists, rankings, values and paths.

Not every field is scored. In these 63 questions, `element_type` is descriptive
information and does not change the score. Depending on what the question asks,
the evaluator scores identifiers, labels, requested attributes, values, ranks,
or ordered path steps.

A small list answer looks like this:

```json
{
  "answer_type": "list",
  "status": "ok",
  "results": [
    {
      "identifier": "http://www.omilab.org#Task_BPMN-example",
      "label": "Example task",
      "element_type": "task_bpmn",
      "rank": null,
      "attributes": [],
      "related_elements": []
    }
  ]
}
```

The complete format is in
[answer_schema.json](scripts/schema/answer_schema.json).

## What the evaluator does

[evaluate_generated_answers.py](scripts/evaluate_generated_answers.py) follows
these steps:

1. It loads the answer schema and gold answers.
2. It reads either the saved transcripts or an existing predictions JSONL file.
3. When reading transcripts, it finds the first answer to the experiment
   question.
4. It puts every prediction into one consistent JSONL file. `query_id` tells us
   which question it answers; `run_id` tells us which attempt it came from.
5. It checks whether all expected question/run combinations exist. In this
   experiment, that means 63 questions × 3 runs = 189 predictions.
6. It checks the answer format and compares every valid prediction with its gold
   answer.
7. It calculates scores for each run, then reports averages overall, for C1–C6,
   for yes/no and structured answers, for each question and for runs 1–3.
8. It writes the detailed JSON report and the simpler per-run CSV file.

The normalized predictions in step 4 are not new model answers. They are the
same answers extracted from the transcripts and stored in a predictable format.

The evaluator does not query GraphDB and does not decide what the correct answer
should be. It treats the supplied gold answers as correct.

## How the scores work

What gets compared depends on the question:

| Answer type | What the evaluator compares |
| --- | --- |
| List | The returned entities and, when requested, their attributes. Order is ignored unless the question asks for an ordered answer. |
| Value | The requested value and unit. Durations are converted to seconds before comparison. |
| Ranking | The entities and their positions. Rank 1 is first, rank 2 is next and tied entities share the same rank. |
| Path | The BPMN elements in their correct order, plus any requested cost or duration. |
| Yes/no | Whether the bare `Yes` or `No` matches the gold answer. |

For a ranking example: if two people are tied for the largest number of assigned
tasks, both have rank 1. The person with the next lower number has rank 2. The
answer receives credit when it returns the correct people with the correct
ranks.

Entities are matched by identifier when possible. If an identifier is missing,
the evaluator can fall back to a normalized label. `related_elements` are
ignored in ordinary answers, but they can be used to store an ordered path.

Paths receive partial credit. Suppose the gold path is `A → B → C`, while the
generated path is `A → C`. `A` and `C` still match because they remain in the
correct relative order. `B` is missing, so recall goes down. An extra incorrect
step would reduce precision. Either problem can lower F1. If the question also
asks for a path cost or duration, that value is compared too.

A structured answer must be valid JSON and follow the schema. If its JSON cannot
be read or required fields are missing, the run is marked invalid and receives
zero precision, recall and F1.

Some questions allow more than one correct gold representation. C3-023, for
example, accepts both a compact path and a version with expanded subprocesses.
The prediction is compared with both and the better score is kept.

### Precision, recall, F1 and exact answers

- A **true positive** is an expected item or value returned correctly.
- A **false positive** is an extra or incorrect item or value.
- A **false negative** is an expected item or value that was left out.
- **Precision** asks how much of the generated answer was correct.
- **Recall** asks how much of the gold answer was recovered.
- **F1** balances precision and recall.

For example, if the gold list is `A, B, C` and the generated list is `A, C, D`,
then `A` and `C` are true positives, `D` is a false positive and `B` is a false
negative.

`exact_answer` is stricter. It is true only when nothing scored is missing,
nothing scored is extra and a structured answer also has the correct
`answer_type` and `status`.

The script calculates the scores separately for every run and then averages
them. Every run has the same weight, whether the answer contains one fact or
fifty.

Three runs are expected for every question. Normally, the evaluator stops if a
run is missing. With `--allow-incomplete`, it scores the runs that exist and
lists the missing ones in the coverage report. Those missing runs are left out
of the averages; they are not counted as zero.

## What cannot be reproduced exactly

The saved scores can be recalculated exactly from this repository. Generating a
new set of answers is less exact, for a few honest reasons:

- model answers can change from one run to another;
- model and service versions can change; and
- the repository does not contain an automated Codex runner, so the threads and
  transcript exports are created manually.

These limits should be mentioned when reporting results from a new run.

## A short security note

Never commit an OpenAI API key or bearer token. The files in this repository use
placeholders on purpose. Put the real secrets only in the local `.env` file and
paste the bearer token into the temporary Workbench copy of the connector query.

The supplied Weaviate container allows anonymous access because this setup is
meant to run only on your own computer. Do not expose ports 7200, 8000, 8080 or
50051 to an untrusted network without adding authentication and network rules.
